## Bounded action and telemetry patterns

- The stress runner uses `PROFILE_EVERY = 60` and a minimum 1,200-second run (`phase04_stress_browser_retry01.py:23–32`). `checkpoint(page, reason)` collects compact game state plus heap/DOM/storage/save latency (`:~110–145`); `maybe_profile`/checkpoint scheduling provides bounded time-based telemetry. `browser-stress.md` documents the passing 20-minute run and distinguishes the last scheduled telemetry checkpoint from the true final game-state snapshot.
- The 30–60-minute adventure reference is `phase04_adventure_playtest_retry01.py`: `action()` increments an operation counter and triggers a scheduled checkpoint (`:143–150`); `checkpoint()` stores a focused snapshot and schedules the next checkpoint 60 seconds later (`:471–499`). `decisionLog`, `progressLog`, and `lootDroughts` capture decisions/findings rather than full page/DOM dumps.
- Adaptation pitfall: do not rewrite a growing whole-result JSON snapshot after every action. `write_recorded` archives each full published body, multiplying storage with every update. Prefer append-only raw operation JSONL, periodic compact checkpoint projections, and a final summary; keep full failure evidence in unique files.
- Adaptation pitfall: close/transition can detach modal rows. Do not keep a Playwright `Locator` across a close, reload, or rerender; reacquire the locator after the transition and wait for visible/open state. Avoid broad text matching for `灰狼`: `傷痕灰狼` contains the same substring. Use stable IDs such as `.wolf-track-row[data-wolf-track="grayWolf"]` and then query within that row. The Phase 4 harness had a failed first attempt when it tried to read a reward row after its dialog had closed; `browser-stress.md` preserves the finding and the separate passing retry.
