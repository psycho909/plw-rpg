## Optional-family-marker compatibility concern

A separate spec review described an active Wolf King save with `combat.familyEncounter` removed as a root-form crossguard bypass. I do not classify this as a scoped normal-runtime defect under the explicit exclusion of file tampering/deletion. A live family-tagged boss does not naturally lose only its family marker: the legacy `combatTurn(..., 'run')` route clears `state.combat` entirely, and death also clears combat; flee/death intentionally preserve the wolf boss root for re-challenge. Re-tracking then reconstructs the tagged encounter from that root (`src/engine/actions.ts:163-165`; `src/engine/simulation.ts:120-124`; `src/engine/wolfFamily.ts:152-161`; `src/services/rewardSave.test.ts:130-147`).

The same persisted root can legitimately coexist with an active untagged legacy wolf after flee/death. The forest UI still exposes “尋找怪物” through the legacy `encounter(state)` route, whose low-threat candidates include the untagged outdoor wolf (`src/components/PlaceWindow.vue:45`; `src/engine/actions.ts:135-150`; `src/data/config.ts:33-37`). The ticket explicitly makes `familyEncounter` optional and preserves untagged legacy wolf/dungeon saves (`tickets/20261006-v2x-03-monster-slice.md:37`; `src/services/rewardSave.test.ts:150-158`). Therefore root-form presence alone cannot mean the current untagged wolf is a tagged boss. Rejecting all untagged outdoor wolf saves while any boss root exists would break this valid compatibility path. The exact proposed “remove the marker from a currently tagged boss save” case is an externally modified save and cannot be distinguished from the supported legacy shape without a schema/provenance change. The existing strict guard still validates canonical stats/root identity whenever `familyEncounter` is present (`src/services/rewardValidation.ts:199-220`). No P2 normal-runtime finding is confirmed from this concern; no source change or new test was made.
