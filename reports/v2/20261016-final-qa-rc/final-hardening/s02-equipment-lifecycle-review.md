# S-02 — Defender Equipment Lifecycle：設計審查

- 日期：2026-10-16。Ticket：[20261016-v2x-final-data-integrity](../../../../tickets/20261016-v2x-final-data-integrity.md)。
- 結論：**OWNER DECISION REQUIRED**。在既有 schema 下，Owner 規則只有一種情境無法安全實現：ledger 已經 16 筆時。要解決必須改 ledger 契約或 save 驗證，依授權停止實作。
- 產品 Source 沒有修改，只擴充了特性測試 `src/engine/postRcS02Defender.test.ts`（Codex `luna-medium-s02-matrix`，3 個檔案 37 項測試通過）。

## 1. 現況與 Owner 規則對照

| 情境 | 目前行為 | 是否符合 Owner 規則 |
|---|---|---|
| 防衛者存活 | 裝備計入防衛能力 | ✓ |
| 暫時受傷（`injuredUntil`） | 效果暫停，ledger 紀錄保留，不釋放額度；存讀檔後一致 | ✓ |
| 受傷後恢復 | 同一筆紀錄的效果恢復 | ✓ |
| 永久死亡，ledger 未滿 16 筆 | 效果立即停止；補位者可以接受新裝備；不退還、不轉交 | ✓ |
| 被選為接班人 | 離開防衛名單，效果停止，紀錄保留 | ✓（額度同樣受 16 筆上限限制） |
| 重複交付同一個 `instanceId` | 拒絕，物品、金幣、ledger 都不變 | ✓ |
| 製作者聲望 | 死者那筆紀錄仍計入累積門檻；跨過門檻只發一次，之後不會重複發 | ✓（沒有重複獎勵） |
| 危機結算、存讀檔、determinism | 結算一致；中途重載與連續執行的序列化狀態相同；死者裝備不計入當下防衛能力，但保留在歷史 | ✓ |
| **嚴重度 3、ledger 已 16 筆、有人永久死亡** | 效果停止，但 16 筆全域上限已滿，補位者**無法**接受新裝備 | **✗** |

所以，除了 ledger 已滿這個邊界，Owner 規則的其他部分**在目前的程式碼裡都已經成立**。

## 2. 為什麼在既有 schema 下做不到

- `CrisisEquipmentAllocation` 的 ledger 同時扮演三個角色：有效分配、捐贈歷史（donor、`sourceItem` 快照）、製作者聲望門檻的累積依據（`regionalCrisisRecognition.ts:45-52` 會加總**所有**紀錄）。
- `saveService.ts:149-175` 驗證 `equipment.length ≤ 16`，而且每個 `defenderNpcId:slot` 只能有一筆。
- 嚴重度 3 時，有效欄位是 8 人 × 2 = 16，剛好等於 ledger 上限，只要有一人永久失格就沒有空間了。

既有 schema 下可以考慮的做法都會違反至少一個不變條件：

| 做法 | 違反的條件 |
|---|---|
| A. 覆寫或刪除死者的紀錄 | 歷史不可追溯（#2）。製作者的累積效果會下降，之後再交付可能**重複跨過門檻、重複發放聲望**（#4） |
| B. 忽略死者紀錄，繼續往 ledger 新增 | ledger 會超過 16 筆，**存檔無法讀取**（#5、#8）；Owner 也明確禁止這樣做 |
| C. 只在 ledger 未滿時允許補位（現況） | 滿額時無法補位（就是本 finding） |

## 3. 需要 Owner 授權的最小設計

**方案 S2-A：ledger 改成「有效上限 16、歷史上限 32」（建議）**

- 契約：`equipment` 仍是一個陣列，紀錄的形狀不變，不需要 migration。
  - save 驗證的長度上限從 16 改成 32（`REGIONAL_CRISIS_CONTRIBUTION_LIMITS` 增加歷史上限常數）。
  - 交付時改成檢查「有效紀錄 < 16」，有效紀錄是指防衛者仍在有效名單、且不是永久失格的那幾筆；同時檢查「全部紀錄 < 32」。
  - 每個 `defenderNpcId:slot` 只能有一筆的規則保留。
- 聲望門檻繼續加總所有紀錄，所以不會重複發放；歷史完整保留。
- 相容性：舊存檔（≤16 筆）可以直接讀。**新存檔超過 16 筆時，舊版 build 會拒絕讀取**，等於不能降版，需要 Owner 接受。
- 需要定義「永久失格」：建議是死亡、被選為接班人、職涯退休。**轉職離開 guard／mercenary 目前沒有定義**，它可能會再轉回來，請 Owner 決定算不算永久。
- 32 筆上限的理由：嚴重度 3 時，原本 16 筆，加上最多 16 筆補位。超過時沿用既有的「沒有可用欄位」訊息拒絕。

**方案 S2-B：拆成有效分配與歷史兩個欄位**

- 歷史資訊最完整，但會改變紀錄形狀，需要 save migration 和更多驗證，風險高於 S2-A。

**方案 S2-C：維持現況**

- 已知限制：只在嚴重度 3、ledger 已滿後又有人永久失格時發生。影響是那一場危機的防衛效果較低，不會造成資料損毀。

測試檔：`postRcS02Defender.test.ts`。

- 已涵蓋：存活、暫時受傷、恢復、未滿額時永久死亡＋補位、滿額時永久死亡、接班人、重複交付、聲望不重複、存讀檔、危機結算、determinism。

## 5. 判定

- S-02：**OWNER DECISION REQUIRED**。建議方案 S2-A，需要授權修改 save 驗證上限，並定義「永久失格」。
- 不影響目前的 Release Blocker 判斷：這不會造成資料損毀，影響範圍只限於滿額的嚴重度 3 危機。
