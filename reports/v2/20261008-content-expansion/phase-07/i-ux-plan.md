## Product direction and scope

Oakvale is a Traditional Chinese, world-first retro RPG. This slice helps a player find useful discoveries among the frozen Phase 7 content without turning the world screen into a catalog dashboard. The content snapshot to cover is 48 equipment bases, 24 recipes, 59 materials and 66 authored monsters; implementation must re-count against the actual Root-frozen registry and must not confuse equipment instances with bases or count duplicated crop-good mirrors twice.

Use the existing world and local `PixelWindow` flows. Add only contextual local search, existing/native filters, useful family or use grouping, bounded paging where a list is long, discovery state, source/use explanations, and readable Boss/crop guidance. Keep Traditional Chinese, monochrome pixel borders, existing tokens and short text hierarchy. Do not add a codex route, dashboard, new navigation, component library, persistent HUD, URL state, or new simulation rules. Search/filter state is transient and resets with its existing window, consistent with `docs/UI.md`.

No new warning modal or discovery toast: Boss and discovery guidance stays inline in its current world/window context; actual outcomes continue through `StatusNotice.vue` / `gameStore.message`. Opening a `PixelWindow` continues to leave world time running. Do not pause or otherwise change active Idle progression.

## Interaction and state requirements

- Search is local, immediate and transient: visible label, IME-safe text input, accessible clear button when nonempty (clear immediately and return focus), filtered result count, separate empty-data and no-match copy. No network debounce or URL/storage persistence.
- Search and filter apply before paging. Gear remains capped at 20 per page; page resets/clamps on query/filter/ownership changes. Avoid adding pagination to short lists unless the frozen content/runtime data demonstrates it is needed.
- Native filter buttons remain real buttons with `aria-pressed`, keyboard focus and selected-state text/border treatment. All new actions are buttons; navigation remains a link only if the current app has a real route (it does not here).
- Disabled encounter/crop/recipe actions have nearby text reasons and `aria-describedby` where a stable helper ID is practical. No disabled-only explanation and no hover-only information.
- Source/use labels distinguish known source, not-yet-discovered region and known-but-currently-ineligible condition. Search must not disclose hidden region identity or turn hidden content into a visible global catalogue.
- Discovery status text is textual and persistent only when the canonical collection state says so. The existing `loot.item` live status stays bounded to its existing event buffer; do not synthesize a “new” flag later from history or item ownership.
- Boss rank, variants and telegraphs are textual. The encounter projection provides eligibility; `AdventureWindow` provides the current-turn cue. Boss guidance is inline and does not steal focus or pause the world.
- Crops show the engine's current valid season/region and plot-capacity outcome; growth/harvest/help copy must use released crop data. Do not imply that an unavailable choice is selectable or that a material is consumable without its released consumer action.
- Desktop keeps the map visible behind the existing window. At 768px and 360px, controls wrap and detail follows the list; the existing `PixelWindow` body owns long-content scroll and safe-area bounds. Important touch actions target the existing 40px baseline, preferring 44px. No horizontal scrolling is introduced for these lists.

## Browser acceptance plan after release

Use the actual production Chromium runner in `reports/v2/20261008-content-expansion/phase-07/qa_browser_runner.py`; it is currently preparation-only and Root must freeze source/build/content and issue the release manifest before launch. Do not run it now. The standard `regression` mode is 60–300s and covers fresh-world visible controls, regular one-day progression, pause/save/reload equivalence. The `content-agent` mode is 1800–3600s (minimum 30 minutes) and explores visible semantic action families without injecting state; `stress` is 1200–1800s. Controlled family/Boss fixtures use their separate hash-pinned contexts and prove only exact targeted UI/reload behavior, never natural acquisition/reachability. Use regression plus a controlled selector-driven I smoke for UI acceptance; long modes remain K/release gates.

- Gear/discovery: `dialog [data-instance-id]`, `[data-gear-comparison]`, `.gear-pagination`, `[data-loot-feedback]`.

The runner's current `classify_button()` already recognizes observe, explore, combat, loot, craft, use/equip, shop, farm, crisis and advance actions; retain that taxonomy. Extend the runner with narrowly scoped exact-label/selector assertions for search clear/no-results, filter-and-page reset, known/unknown material sources, current-region rank/Boss cue, crop availability/reason, keyboard focus, and 360px layout. Use a fresh normal browser context for natural paths; use fixture injection only in its isolated controlled lane. Capture screenshots and visible labels; assert no new modal and that world time continues while a discovery window is open.

I-specific checks after the release: search found/no-match/clear; every filter and 20-item paging boundary; page clamp after selection changes; source/use for a material with multiple sources, undiscovered region and known source blocked by a condition; recipe missing/satisfied input and exact `planCraft` rejection text; each crop availability reason and an available crop lifecycle; local Boss rank/eligibility and active turn cue; keyboard-only operation, focus visibility/restoration and accessible names; zh-TW long labels at desktop, 768px and 360px; open window remains scrollable and active world time advances. Full source/save/reload equivalence remains the runner regression contract; do not claim a fixture establishes organic reachability.

## Current readiness and blockers

The repository already has the strongest owners: `InventoryWindow`/`rewardProjection`, `PlaceWindow`/`craftingProjection`, `AdventureWindow`/`contentCombatPresentation`, `contentEncounterOptions`, `contentSourceHints`, `PropertyWindow`, `LifeNewsWindow`, `PixelWindow`, `StatusNotice` and `gameStore.act`. The principal gap is UI consumption and the context-aware source/crop exposure required by the released G/H API. Current `contentSourceHints(contentId)` returns flat source/use strings without state-aware undiscovered-region vs eligibility metadata; current `contentEncounterOptions(state)` is an engine-owned canonical eligibility query, but its full output must not be rendered as a global catalog. Current farm UI is wheat-shaped and has no crop-choice control. Existing HTML has no crop or Phase 7 content search selectors.

F remains in progress and G/H are not released in their tickets at preparation time; I is blocked by H in its approved ticket. Therefore the source/API seams above are conditional on accepted F/G/H contracts and Root's explicit I release. If a released projection cannot distinguish hidden, unavailable and eligible content without UI predicate duplication, stop at that exact seam and return it to Root for a canonical decision. No source implementation, test, build, Browser process, commit or publication is authorized by this preparation plan.
