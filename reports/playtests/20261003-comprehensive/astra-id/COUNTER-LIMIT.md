# Counter 極端上限疑慮：唯讀處置建議

日期：2026-10-03 UTC。來源：獨立 reviewer 對新版 `counter < Number.MAX_SAFE_INTEGER` 的邊界疑慮；依使用者要求由 Astra 評估。範圍為唯讀收尾，不修改已凍結 runtime 或重新定義 UID。

## 結論

**疑慮成立。建議保留目前實用的整數／相對 ID 防護，將極端 counter 耗盡列為低優先級已知限制，由主 Agent 記入交付風險。** 這不是假陽性，也不宣稱目前 guard 保證所有被接受的受控極端存檔可無限續玩。

先前 REPORT.md「保留一次遞增空間」只代表下一次算術結果仍為安全整數，**不代表遞增後仍符合目前反序列化上限**。本補充是該敘述的明確限定；不能以此短語當作續存可讀性的證明。

## 為何不以另一個常數修補

- 把 `< MAX_SAFE_INTEGER` 改成 `<= MAX_SAFE_INTEGER` 可讓以上一次遞增結果讀回，但再一次遞增仍會超出安全整數，之後存在重複 ID／不安全狀態。這只移動失敗點，不能稱為真正續玩修復。
- 把上限降低為 MAX−2、MAX−100 或其他任意值，只會製造另一個被接受值經活動抵達拒絕邊界的案例。
- 飽和不再遞增會重用 ID；重新編號需要完整處理既有角色、作物、事件與歷史等引用；BigInt／字串 ID 改變 schema。這些都不適合在凍結後以小 guard 假裝解決。

無需重設 UID 的可靠方向是**執行期耗盡政策**：所有 ID 配發集中檢查，耗盡時在任何部分狀態修改前拒絕需要新 ID 的活動／模擬交易，仍允許保存並提供清楚的耗盡訊息。此方案需涵蓋 `emit()`、作物直接遞增、NPC 配發及其呼叫者的交易邊界，並確保批次模擬不半途改寫後才失敗；不是僅修改 deserialize 一行，也不是目前已驗證範圍內的低風險補丁。

## 風險分級與限制

這個失敗已在**受控注入接近 9×10^15 的 counter** 下確認。現有正常新世界、耕作、死亡／繼承及 500 年測試未出現此值；目前沒有正常使用可實際抵達此極端邊界的證據，但不把有限數值在數學上稱為永遠不會耗盡。

本次已修復的可重現低值回退、與現存 ID 衝突及 crop 重複問題不因此失效。極端上限案例仍是未修復限制，應與已修復的 continuation 問題分開列示；不是「所有損壞存檔均安全」的驗收承諾。若未來要求所有合法匯入 counter 在耗盡後也能安全保存，應新增明確 runtime 耗盡政策與對應交易回歸，而非持續調整靜態上限。
